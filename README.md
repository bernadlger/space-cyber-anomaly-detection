# 🛰️ Space Cyber Anomaly Detection

## Overview

A reaction wheel is a precision device used on satellites and spacecraft to control their orientation (attitude) without using thrusters or expelling propellant. A reaction wheel is essentially a flywheel, which is a heavy disk mounted on a motor. When the motor spins the wheel in one direction, the spacecraft rotates in the opposite direction due to the conservation of angular momentum. By adjusting the wheel's speed, the spacecraft can perform very fine pointing maneuvers, ideal for stabilizing telescopes, antennas, or cameras. [[source]](https://github.com/jwd164/space-cyber-anomaly-detection-dataset/blob/main/notebooks/scad_introduction.ipynb)


An anomaly occurs when one of these reaction wheel values is overridden indefinitely, this is the cyber effect simulated in the [SCAD Dataset](https://github.com/jwd164/space-cyber-anomaly-detection-dataset). The goal of this project is to detect this kind of anomaly directly from a satellite's telemetry using machine learning, determining whether an attack is present, and if so, identifying which of the three reaction wheels was targeted.

## 📡 Dataset

### What is the SCAD Dataset?

The SCAD dataset is a collection of hypothetical FireSat satellite telemetry generated by a high fidelity modeling and simulation environment called ACORN. The telemetry data is representative of the data provided to and by the flight software of the FireSat.

FireSat (short for Fire Satellite) is a conceptual, and often hypothesized satellite system designed specifically for global wildfire detection, monitoring, and response coordination.

SCAD is time series data stored in comma separated value (CSV) files. The dataset contains both baseline mission data as well as data where cyber effects were introduced [[source]](https://github.com/jwd164/space-cyber-anomaly-detection-dataset/blob/main/notebooks/scad_introduction.ipynb).

### Dataset Composition

Each data file captures 10 minutes of telemetry sampled at 1 Hz. This project uses the following scenarios from the dataset:

- **Baseline** — normal satellite operation, no attack present.
- **Attack_RWA** — reaction wheel A is targeted.
- **Attack_RWB** — reaction wheel B is targeted.
- **Attack_RWC** — reaction wheel C is targeted.

## 📓 Notebook Overview
The project follows a four-stage pipeline: raw telemetry data is first explored and validated, then cleaned and reduced to a selected set of features, and finally used to train two separate XGBoost models, one for detecting whether an attack is present, and another for identifying which reaction wheel was targeted.

### 01: Exploratory Data Analysis (EDA)

- Explored the raw telemetry files and confirmed the feature structure: **baseline files contain 140 features**, while **attack files contain 141** (the extra column being `AttackIntensity`); the remaining 140 features are identical across both scenarios.
- Reviewed all 140 features individually to identify which ones could reveal the satellite's rotational/attitude changes at the moment of an attack on a reaction wheel.
- Excluded features that were:
  - Unaffected by the attack (e.g. orbital parameters),
  - Constant / without variance (not useful for an ML model),
  - Binary or multi-class flags,
  - At risk of data leakage.
- This narrowed the feature set down to **26 selected features**, considered the most relevant for detecting attack-related changes.
- Plotted **time series visualizations** of these 26 features for both baseline and attack files, to visually observe how they behave around the attack point.
- Plotted **KDE (Kernel Density Estimate) distributions** of the same 26 features to compare baseline vs. attack value distributions, independent of the time dimension.

### 02: Preprocessing

- Scanned all CSV files individually to detect row/column mismatches or missing values within the 26 selected features.
- Dropped the problematic files (2 out of 1920) from the metadata, resulting in a clean dataset of 1918 files.
- Reduced each remaining CSV to the 26 selected features and added a `label_binary` column (baseline → 0, attack → 1).

### 03: Binary Classification

- Trained an XGBoost model using all 26 selected features to detect whether a given telemetry sample is anomalous (attack) or normal (baseline). *(Results reported in the Results section.)*
- However, feature importance analysis revealed that a single feature (`TotalTorqueRodCommand[2]`) accounted for ~58% of total importance, and the top 5 features (`TotalTorqueRodCommand[0,1,2]` and `SensedWheelSpeed__RWA_B/C`) together accounted for ~85%. This was also consistent with the earlier time series visualizations, where these same features showed a clear, direct shift right at the attack point, unlike the other features.
- The dataset providers had suggested trying to train without the "primary affected columns" (the ones directly affected by the attack), without specifying which ones. Based on both the feature importance results and the time series visualizations, `SensedWheelSpeed__RWA_A/B/C` and `TotalTorqueRodCommand[0,1,2]` were identified as these primary affected columns, and the model was retrained on the remaining **20 features** to test whether meaningful signal still remained without them.

### 04: Multiclass Classification

- Filtered out the pre-attack (baseline) rows from the attack files, keeping only the rows recorded after the attack start time, since the goal here is to identify which wheel was attacked, not whether an attack occurred.
- Trained an XGBoost model on the same 26 features to classify the attacked wheel (RWA, RWB, or RWC). *(Results reported in the Results section.)*
- Unlike the binary task, removing "primary affected" columns here follows different reasoning: once an attack is confirmed, `SensedWheelSpeed__RWA_A/B/C` being the most important features is expected, since they are the core signal directly tied to each wheel, so there was no need to question the model's reliance on them.
- Instead, a robustness check was run for a more realistic scenario: what if the wheel speed sensors themselves failed or stopped reporting during an attack? To test this, `SensedWheelSpeed__RWA_A/B/C` were removed and the model was retrained on the remaining features to see how well it could still identify the attacked wheel.

This drop in performance is expected: with `SensedWheelSpeed__RWA_A/B/C` removed, the model loses the most direct and informative signal for identifying which wheel is affected, and is forced to rely on more indirect, downstream features (`TotalTorqueRodCommand`, `AngVelMag_B_I`, `DesiredWheelCommand`, etc.).

The train/test gap also widens noticeably compared to the full-feature model (Accuracy: 0.0766, Precision: 0.0764, Recall: 0.0766, F1: 0.0767, AUC: 0.0278), and train performance itself drops to ~93% instead of ~100%. This pattern, lower train performance combined with a larger train/test gap, suggests the model is underfitting on the training data (it can no longer learn the task as cleanly without the wheel speed signals) while also showing mild overfitting relative to how well it fits the training set. In other words, without the primary wheel speed sensors, the remaining features still carry a meaningful, learnable signal (~85% accuracy is well above chance), but they are a much weaker substitute for identifying the attacked wheel.
